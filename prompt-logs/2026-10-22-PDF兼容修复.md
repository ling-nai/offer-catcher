# 2026-10-22 PDF 兼容修复（Bugfix）

- 目标：修复上传任何 PDF 都报「PDF 解析失败（a.toHex is not a function）」的阻断性问题
- 报错现象：任意 PDF（含正常文件）上传后必现 `a.toHex is not a function`，与文件本身无关，重新选择文件也无法绕过
- 根因：pdfjs-dist 6.x 默认构建在 worker 内调用 ES2025 新 API `Uint8Array.prototype.toHex`，Chrome 140 之前的内核不支持该 API，解析链路第一步即抛错
- 我的 Prompt（原文）：要求 worker 与主线程同步切换 pdfjs-dist legacy 构建（官方自带 polyfill；两条线程一新一旧会以同样方式报错）、`getDocument` 传参改为 `new Uint8Array(buffer)`，不改其他逻辑、不改错误文案、不升级/降级版本
- AI 的实施：
  - `src/lib/pdf.ts` 仅 3 处修改：worker 地址 → `pdfjs-dist/legacy/build/pdf.worker.min.mjs?url`；主线程动态 import → `pdfjs-dist/legacy/build/pdf.mjs`；`getDocument({ data: new Uint8Array(buffer) })`
  - 错误文案、解析流程、依赖版本（pdfjs-dist 6.4.299）均未改动
- 测试/验证：
  - `npm run build` 通过（legacy 构建自带 pdf.d.mts 类型声明，TS 无报错）；`oxlint` 0 警告 0 错误
  - 产物确认：worker 1.32MB、主线程 pdf chunk 487KB，均为 legacy 构建；主包体积不受影响（仍是动态 import 分包）
  - 待人工验证：在低版本内核浏览器（Chrome <140）上传文字版 PDF，确认不再报 toHex 错误且文本正常填入；现代内核浏览器回归一次上传流程
- 我的人工调整：无（按要求最小改动）
- commit：fix: 改用 pdfjs legacy 构建修复旧内核浏览器上传 PDF 报错
